# 最小安全通道设计

本文是 DSH Remote 端到端加密的**最小实现规范**。目标是：层次清晰、功能尽可能少、每一层只做一件事，并且小到可以人工论证没有漏洞。

威胁模型与推演过程见 [审查](e2ee-and-transport-review.md)；线协议仍以 [protocol.md](../protocol.md) 为准。

---

## 1. 目标与非目标

信任输入只有两个带外通道：**Host 本地渲染的二维码**，和**用户在一块屏幕上读到、在另一块屏幕上手动输入的配对码**。两者都不经过 Server。

**目标**：在 Server 完全敌对的前提下，让 Host 与 Client 之间的业务内容不可读、不可改，且 Server 无法冒充任一端的设备身份。

**非目标**（明确不做，这些是简化预算）：

- 多用户 / 多账号共享设备的信任传递
- 设备撤销的在线协商（撤销 = 删本地 pin）
- 密钥轮换 UI（换密钥 = 重新配对）
- 抗量子（等 Noise 库支持混合套件再加，见 §8）
- 匿名性 / 隐藏 IP / 隐藏通信时间
- 端点被入侵后的保护

## 2.0 角色对照（先对齐名字）

本文与仓库代码使用不同的名字，实现时按这张表换算：

| 业务叫法 | 是什么 | 仓库代码里的名字 | 谁持有对话内容 | 有无摄像头 |
| --- | --- | --- | --- | --- |
| **client** | DSH 实例 | Host（Plugin） | **是**，全部会话与工作区 | 通常没有（可能无头） |
| **controller** | 手机 | Client（Android/VS Code/Desktop） | 只接收投影 | 有 |
| **host** | 中继服务器 | Server | **没有**，只见密文 | — |

### 2.0.1 host（服务器）到底负责什么

它不参与身份锚定，但**没有它连不上**。职责共五项，全部是"让连接能发生"，不是"证明你是谁"：

| 职责 | 内容 | 它因此能看到 |
| --- | --- | --- |
| 1. 注册与凭据 | controller 登录账号或领码注册，换取 device token | 谁的设备、角色、公钥（公开信息） |
| 2. 设备目录与在线状态 | 提供 deviceId 列表与 presence | 设备在线时间 |
| 3. 连接协调 | 分配 `connectionId`，转发 `connect.request/incoming/accepted` | 谁在连谁、连了多久 |
| 4. 信令转发 | 转发 SDP / ICE（WebRTC 协商必需） | 双方的网络候选（IP） |
| 5. 密文中继 | 无法直连时转发 Noise 密文 | 密文长度、方向、时序 |

**它不负责**：提供对端公钥作为信任依据、参与确认码计算、决定谁是本人。这三件事由二维码和确认码完成。

由此得到一句必须成立的分工：

```text
服务器管"能不能连"（授权 / membership）
配对  管"是不是本人"（认证 / 身份）
两者同时成立才允许业务；服务器单独可以拒绝，但不能伪造
```

据此确定两个带外方向，**不要按代码里的 Host/Client 直觉反推**：

- 二维码由 **client（DSH）** 显示，因为它是持有数据、需要被确认身份的一端，而且它可以没有摄像头；
- 确认码由 **controller（手机）** 显示、**client（DSH）** 输入，因为手机有屏幕而 DSH 端有键盘/终端。

## 2. 四层结构

一层只做一件事，层与层之间只通过明确定义的边界交互。

```text
┌──────────────────────────────────────────────────────┐
│ L3 授权   allowlist：已认证的对端能调用哪些 API        │  知道"能做什么"
├──────────────────────────────────────────────────────┤
│ L2 身份   二维码 + 确认码：这把公钥属于谁              │  知道"谁是谁"
├──────────────────────────────────────────────────────┤
│ L1 加密   Noise IK：内容机密性与完整性                 │  知道"说了什么"
├──────────────────────────────────────────────────────┤
│ L0 传输   Relay / WebRTC：搬运字节，不可信             │  不知道任何事
└──────────────────────────────────────────────────────┘
```

| 层 | 职责 | 失守后果 | 依赖 |
| --- | --- | --- | --- |
| L0 | 搬运 | 无（不可信是设计前提） | 无 |
| L1 | 机密性 / 完整性 / 重放 | 内容泄露 | L2 提供对端公钥 |
| L2 | 身份真实性 | 前功尽弃（MITM） | 带外通道（人眼/扫码） |
| L3 | 权限 | 越权调用 | L2 认证结果 |

**关键约束：L2 不能依赖 L0。** 一旦身份锚点从传输层获取，整条链退化。这是本设计唯一不可妥协的地方。

## 3. 只有三样持久数据

| 数据 | 位置 | 生命周期 |
| --- | --- | --- |
| 设备私钥（X25519） | 各设备本地，`0600` | 永久，直到重装 |
| pin 表（对端 deviceId → 公钥 + 来源） | 各设备本地，按 server origin 分目录 | 删 pin 即解除信任 |
| 一次性 nonce | 仅配对期间存在内存 | 5 分钟或成功后立即销毁 |

没有证书链、没有 CA、没有密钥服务器、没有口令派生。**私钥不出设备，公钥靠人眼传递一次。**

## 4. 首次配对（只发生一次）

两个方向用的**不是同一个码**，名字必须分开叫，否则实现时极易接错：

| 名称 | 方向 | 承载什么 | 长度 | 为什么是这个长度 |
| --- | --- | --- | --- | --- |
| **配对码**（二维码） | Host → Client | Host 公钥 + deviceId + nonce + 过期时间 | 约 130 字节 | 必须真的把 32 字节公钥送过去，压不成几个字符 |
| **确认码**（SAS） | Client → Host | 由**双方**公钥 + nonce 派生的摘要 | 12 位 base32（60 bit） | 不传密钥，只做人眼比对；短于此会被离线碰撞 |

关键区别：配对码**携带**密钥，必须有足够长度；确认码**验证**密钥，必须短到能读，但不能短到能被枚举。

> 曾经写过的"用 8 位短码做配对码"是错的：8 个字符承载不了 32 字节公钥，而"短码 → 公钥"的映射表如果放在 Server 上，等于把信任锚交回给对手（违反 I2）。

```text
client (DSH)                                  controller (手机)
 │  ① 在 client 上执行 /remote pair
 │  ② Host 本地生成 nonce（32B，单次）
 │  ③ client 屏幕显示二维码：
 │     dshpair://v1?h=<hostDeviceId>&k=<hostPub>&n=<nonce>&e=<exp>
 │                                            │
 │                                            │  ④ 扫码
 │                                            │  ⑤ pin(hostDeviceId → hostPub)
 │                                            │     来源 = pairing
 │  ⑥ Noise IK 建立（rs = 二维码里的 hostPub）
 │                                            │
 │  ⑦ 两端各算 SAS = HKDF(hostPub, clientPub, nonce)[:12]  (60 bit base32)
 │  ⑧ 用户读 controller 屏幕上的确认码，输入 client
 │  ⑨ client 用"通道里的 controller 公钥"算出确认码并与输入比对
 │        一致 → pin(clientDeviceId → 通道 clientPub)，来源 = pairing
 │        不一致 → 立刻断开连接
 │  ⑩ nonce 销毁；两端状态变为 ready
```

要点：

- ③ 的二维码由 Host **本地**生成，绝不经 Server（不变量 I2）。
- ⑧ 用户读的是**手机的屏幕**，不是 Host 的屏幕；Host 在输入前不显示自己算出的值（I5）。
- ⑨ 用通道里的 `clientPub` 算 SAS 再比对，等价于验证"通道里那把公钥就是手机上那把"。
- ⑩ nonce 单次使用（I7）。

### 4.1 为什么不用 XOR 掩码传证书

一个自然的想法：把证书与二维码里的密钥异或，掩码后走通道，收到再解。逐条核过，不采用。

**先纠正前提**：Noise IK **不传证书**。双方 static 公钥在配对时已各自 pin 住，会话密钥由每连接的临时 DH 派生，从不上线。所以"再加密后传输真正用于通讯的证书"这一步在本架构里不存在，也就没有需要掩码的对象。

即便如此，XOR 掩码本身也不如承诺方案：

| 维度 | XOR 掩码（OTP） | 哈希承诺（本设计） |
| --- | --- | --- |
| 二维码容量 | 必须与证书**等长**（PQ 证书 1.3 KB → 二维码装不下） | 固定 32 字节 |
| 完整性 | **无**。可延展：已知明文前缀可反推出对应 OTP 字节，从而定向改写字段 | 自动具备，任何改动当场暴露 |
| 密钥复用 | 只能用一次，复用即破 | 无此限制 |
| 短密钥情形 | 重复密钥异或 = Vigenère，直接可破 | 不涉及 |

实测（`DSH1` 魔数 + 版本 + 算法 ID 为已知前缀，算法 ID 从 `0x01` 定向改成 `0x00`）：

```text
接收方解出的算法字段: 0x0（原值 0x1）
魔数与版本仍然合法: 4453483101 1
=> 接收方无法区分"被定向篡改"和"正常证书"
```

同样的改动在承诺方案下哈希立即不一致。

**结论**：二维码只承载**承诺**（32 字节哈希）或**公钥本身**，不承载掩码密钥；证书/公钥若必须经通道传输，一律带完整性校验。若将来要传 PQ 大证书，用 BC-UR 动画二维码，仍不需要 XOR。

## 5. 日常连接（唯一路径，无分支）

```text
1. Client 查本地 pin → 得到 hostPub
2. Noise IK（rs = hostPub），prologue 绑定 connectionId + 双方 deviceId
3. 握手完成 → 通道进入 ready
4. 业务帧（rpc/event）只能在 ready 状态下发送
```

没有第二条路径。没有"如果没 pin 就先信一次"。没有"如果 Server 说 key 变了就更新"。

## 6. 连接状态机（四个状态）

```text
        connect.request
              │
              ▼
        ┌──────────┐  Noise 完成  ┌──────────┐  SAS 通过  ┌───────┐
        │ pending  │────────────▶│ verifying│───────────▶│ ready │
        └──────────┘             └──────────┘            └───────┘
              │                       │                     │
              │ 拒绝/超时              │ SAS 不一致            │ 断开
              ▼                       ▼                     ▼
           closed                  closed                closed
```

| 状态 | 允许的帧 | 说明 |
| --- | --- | --- |
| `pending` | Control 帧 | 尚未完成 Noise 握手 |
| `verifying` | 仅控制面 | 已加密但身份未确认，**业务帧一律拒绝**（I6） |
| `ready` | 全部 | 已 pin 或已完成 SAS |
| `closed` | 无 | 任何异常直接进入，禁止复活 |

已 pin 过的设备重连时，`pending → verifying → ready` 在同一步内完成（无需人工）；未 pin 的设备停留在 `verifying` 等待输入。**两条路径共用同一个状态机，只是推进速度不同。**

### 6.1 候选码独立于连接存活（2026-10-24 修正）

实现早期把「等待确认的连接」和「确认码」绑在一起，实际上跑不通：服务器会在人走到电脑前就关掉空闲连接（实测 `CONNECTION_FAILED`，距握手完成往往不到一分钟），候选码随之消失，确认窗口根本不存在。

修正后的规则：

- 候选码由 `(host 公钥, client 公钥, nonce)` 派生，这三项在整个 offer 生命周期内不变，**重连后仍是同一串码**。
- 候选码保存 peer 身份而不只是 `connectionId`；连接消失后仍可确认。
- 手机端在配对页持续重试连接（间隔 2 秒，直到 offer 过期），用户在电脑上任意时刻确认，下一次重试即通过。
- 确认时若隧道还活着，直接把已认证的 channel 交给连接控制器，不必让手机重连。

### 6.2 手机端三态

设备列表按配对进度分三档，`verification` 只回答「密钥从哪来」，`confirmedAt` 才回答「配对是否完成」：

| 显示 | 条件 | 点击行为 |
| --- | --- | --- |
| 已配对 | `verification=pairing` 且 `confirmedAt` 存在 | 直接连接 |
| 待确认 | `verification=pairing`，`confirmedAt` 缺失 | 进配对页 |
| 未配对 | 其他（含 Server 描述符带来的 key） | 进配对页 |

`confirmedAt` 只在一件事之后写入：**Host 实际转发了业务帧**（`hostDescribe` 返回）。扫码本身不算完成配对，否则手机会对一台从未确认过的电脑反复发起注定被拒的连接。

服务端给的 key 永远进不了「已配对」：`trustDevice` 这个盲信任入口已删除。

## 7. 八条不变量

实现审查以此为准；每条必须有一条回归测试。

| # | 不变量 | 违反后果 |
| --- | --- | --- |
| I1 | 无带外 pin 的设备不得进入 `ready` | 攻击者拿到合法通道 |
| I2 | 配对秘密只在 Host 本地生成 | Server 可自造 pin |
| I3 | pin 不可被任何 descriptor 覆盖 | 密钥替换 |
| I4 | SAS ≥ 40 bit（推荐 60），HKDF 域分离，限次限时 | 离线碰撞 |
| I5 | Host 输入前不显示自身算出的 SAS | 用户照抄 |
| I6 | `verifying` 状态拒绝全部业务帧 | 抢跑 |
| I7 | nonce 单次、5 分钟、单会话独占 | 重放 / 配对互换 |
| I8 | 不提供一键"接受新密钥" | 诱导重配 |

## 8. 刻意不做的事（简化预算）

这些不是"以后再说"，而是**为了可论证而主动放弃**。每一项都写清替代方案，避免被误当成遗漏。

| 不做 | 替代方案 | 理由 |
| --- | --- | --- |
| 证书 / CA / 自签 PKI | 一把公钥 + 一次扫码 | 只有用户自己的几台设备，没有第三方要验证 |
| 内层第二套加密 | 现有 Noise IK | 带外锚已使 MITM 不成立，加层不增加保护 |
| Key transparency 日志 | 人工比对 SAS | 能见面比对，不需要透明日志 |
| 密钥轮换协议 | 重新配对 | 轮换协议的每条消息都是新攻击面 |
| 多设备信任传递（A 信 B 则信 C） | 每台设备各自配对 | 传递会形成信任图，图越大越难论证 |
| 口令 / 密码短语派生 | 无（私钥即身份） | 弱口令是独立的攻击面 |
| 抗量子（当前） | 预留：SAS 与 pin 都与套件无关 | Noise 库支持混合套件后，只换 L1，L2 不动 |
| 自定义 Noise 状态机 | 使用维护中的实现 | 自研密码学状态机是最高风险项 |
| 连接内 rekey | 断开重连 | Noise 已提供连接级前向保密；rekey 是可选优化 |

**判断标准**：任何新功能如果不能用"它防的是哪条攻击"回答，就不加。

## 9. 为什么这个设计可以被人工论证

复杂度是攻击面的主要来源。本设计的规模：

| 指标 | 数量 |
| --- | --- |
| 密码套件 | 1 个（`Noise_IK_25519_ChaChaPoly_SHA256`） |
| 长期密钥 | 每设备 1 把 |
| 持久状态 | 2 类（设备私钥、pin 表） |
| 连接路径 | 1 条 |
| 状态 | 4 个 |
| 人工交互 | 首次 2 步（扫码 + 输码），之后 0 步 |
| 需要信任 Server 的地方 | 0 处（仅可用性） |

在这个规模下，"Server 能做什么"可以被穷举：它只能伪造描述符、伪造连接、调度时序、选择降级、诱导用户。上一份推演的六轮循环已经逐条走过这五种能力，未留下读到明文的路径。

## 12. 可选：传输压缩（用于思维链等高冗余流）

思维链动辄数十 KB，且冗余度极高。压缩放在 **L1 之内的明文侧**（加密前压缩、解密后解压），Server 只看到更短的密文，**不需要任何服务器改动**。

### 12.1 实测数据（本机 Node 26，50 KB 样本）

| 样本 | brotli q4 | zstd L1 | deflate 6 |
| --- | --- | --- | --- |
| 英文散文（README） | 2.74x | 2.51x | — |
| 中英混排技术文档 | 2.23x | 1.96x | — |
| TypeScript 源码 | 4.35x | 3.92x | — |
| 结构化推理（重复标记多） | **10.7x** | 9.1x | 13.4x |

CPU：brotli q4 处理 50 KB 约 5.7 ms；zstd L1 约 1.4 ms。也就是说 **50 KB/s 的思维链只占约 1% 单核**。

规划用 **2.5–4.5x** 做保守估算，结构化推理可达 10x。

### 12.2 对线上字节的影响

```text
50 KB/s 思维链
  → 压缩后 ~11–20 KB/s（按 2.5–4.5x）
  → Noise 开销 +16 B/条，可忽略
  → Relay 帧 base64 膨胀 ×4/3 ≈ 15–27 KB/s
```

顺带一个实际收益：单条消息压到 48 KiB 以下就**不再触发 DSHF 分片**，握手/重组路径不再参与，延迟更稳。

### 12.3 三个必须防的坑

| 坑 | 说明 | 处理 |
| --- | --- | --- |
| **CRIME/BREACH 类长度泄露** | 同一压缩上下文里混入攻击者可控文本与秘密，密文长度会泄密 | 每条消息独立压缩，**不跨消息共享字典**；服务器可控字符串（设备名等）不得进入业务帧 |
| **解压炸弹** | 恶意对端发一个 1 KB 帧解出 1 GB | 限制解压输出上限（对齐 `MAX_SECURE_MESSAGE_BYTES` = 4 MiB）与最大膨胀比（如 200x） |
| **协商被服务器降级** | `hello.ack.capabilities` 是加密前的服务器输入 | 压缩能力**必须在 Noise 通道内协商**，不得依据任何预加密字段决定 |

### 12.4 编解码器选型

| 方案 | 优点 | 代价 | 实现风险 |
| --- | --- | --- | --- |
| `node:zlib` brotli | 比率最好、Node 内置 | Android/browser 无内置，需另找实现 | native 解码器，构造输入就能打崩甚至打穿进程（[CVE-2025-64508](https://github.com/advisories/GHSA-fc2v-vcwj-269v) 即「构造 Brotli 输入触发未认证远程 DoS」） |
| `node:zlib` zstd | 快 | Node 22 不一定有（本机 26 才有），跨端同样缺 | 同上，native 解码器 |
| **`fflate`（deflate，纯 JS）** | 全平台同一份代码，约 8 KB | 比率比 brotli 低约 10–15% | 纯 JS，越界只会抛异常，由 4 MiB 输出上限和 `try/catch` 兜住 |

**推荐先用 `fflate` deflate**：一套代码跑通 Desktop / Android / VS Code，符合"功能少"的原则。

选它不只为跨端一致。**解压器本身就是暴露面**：对端设备一旦被控，它发来的字节会直接喂进解压器，而这条连接的另一头是 Host 主进程。native 解码器出错通常是进程崩溃、极端情况下是内存破坏；纯 JS 实现最坏的结果是抛一个异常，落回"不压缩"即可（§12.5），安全属性不变。

因此即使将来实测发现 deflate 压缩率不够，可选升级也**只能是"通道内协商、默认关闭"**，并同样受 4 MiB 输出上限与膨胀比限制；不会因为"brotli 压得更好"就把它设成默认。

### 12.5 与不变量的关系

压缩**不进入** §7 的八条不变量——它是性能优化，不是安全边界。任何压缩失败、协商失败、膨胀超限都必须**回落到不压缩**，而不是断开连接；但回落本身不得导致任何安全属性变化（业务内容仍在 Noise 之内）。
